# W05 调研笔记：行业机器可读输出共识补充调研

- 背景：`harness-init validate --json` 的机器可读输出与 `.harness/trace/` 落盘策略。trace 格式本体
  已定案（OTel 语义约定字段 + 普通 JSON，见 `W02-验证事件trace格式.md`），本笔记只补四个缺口的
  **行业共识**。
- 日期：2026-09-01；方法：一手来源优先（官方文档/规范原文/官方仓库/本机实测），每条论断标注出处。

## TL;DR 结论

四个缺口各一句话：

1. **结果字段**：静态分析结果互操作的事实标准是 SARIF 2.1.0（4 级枚举 none/note/warning/error，
   修复提示是独立结构化字段 `fixes`）；但各工具原生 JSON 比 SARIF 简单得多（eslint 2 级、ruff 单级
   +独立 `fix` 对象）——**互操作层 3 级 + 独立修复字段，原生层从简**，不存在"必须几级"的强制定论。
2. **落盘策略**：结果报告类（junitxml/eslint -o/pip --report）一律**显式参数才写、固定路径覆盖**；
   运行数据类（Bazel profile/coverage）默认写但语义是"每次运行一份新数据"——Bazel 用**时间戳/调用
   ID 累积 + 保留最近 5 份**，coverage 默认覆盖、显式 `--append` 累积。
3. **stdout 兼容**：**默认人可读 + 显式标志切机器格式**是无争议惯例，6 个独立工具实证一致。
4. **稳定性承诺**：轻量承诺有直接先例——Terraform `format_version`（minor 只增、消费方忽略未知
   字段）与 pip `--report` 的 `version` 字段（只在不兼容变更时变）；JUnit XML 是"不做承诺"的反面
   教材（无官方规范、各家 flavor 分裂）。

对五个具体问题的直接回答：

| 问题 | 回答 | 依据 |
| --- | --- | --- |
| 严重度 2 级还是 3 级 | **面向交换按 3 级建模（note/warning/error），工具内部可用 2 级**；行业无强制定论，但唯一的标准格式（SARIF）是 3 级+none | §1 |
| 修复提示独立字段还是混进 message | **独立字段**。SARIF `fixes[]` 与 ruff `fix` 对象都是结构化独立字段，message 只放人类描述 | §1 |
| 落盘默认开还是显式开 | **显式开**（结果报告场景）。`--json` 打到 stdout 不额外落盘，落盘走显式路径参数；默认写盘只有 Bazel 这种"运行时数据"场景 | §2 |
| 覆盖还是累积 | **结果报告=单文件覆盖是主流**；若要保留历史（数据飞轮场景），先例是"时间戳文件名 + 保留最近 N 份"（Bazel 模式），不是无限累积 | §2 |
| 稳定性承诺形态 | **版本字段 + 只增不改 + 消费方忽略未知字段**，有 Terraform/pip/OTLP 三个直接先例 | §4 |

## 1. 结果字段的行业标准形态：SARIF 是互操作事实标准

### 1.1 SARIF 2.1.0 的 `level` 枚举：4 值（含 none），实际严重度 3 级

- 官方 JSON Schema（OASIS 标准随附、schemastore 托管版）中，`result.level` 与
  `notification.level` 的枚举完全一致：`["none", "note", "warning", "error"]`，
  **默认值 `warning`**。（来源：SARIF 2.1.0 JSON Schema
  https://json.schemastore.org/sarif-2.1.0.json ，逐字核对）
- 即"严重度"维度是 **3 级（note < warning < error）**，`none` 表示"无失败级别"（如纯信息性
  result），不算第四级严重度。
- `result` 对象的**唯一必填字段是 `message`**（schema `"required": ["message"]`）；
  `locations` 是数组（每项 `physicalLocation` = artifactLocation + region 行列区间）；
  **`fixes` 是独立的顶层数组字段**：每个 fix 含 `description` 与 `artifactChanges[]`→
  `replacements[]`（被替换区间 + 替换内容），即"修复建议"在标准里天然是结构化独立字段，不混在
  message 里。（同上，schema `result`/`fix`/`artifactChange` 定义）

### 1.2 哪些主流工具实际输出 SARIF / GitHub 是否只收 SARIF

- **GitHub Code Scanning 的第三方结果上传通道只接受 SARIF**：上传文档全篇围绕"上传 SARIF 文件"，
  无任何其他格式的上传路径；且明确要求 `version` 字段（"Code scanning only supports SARIF version
  `2.1.0`"）与 `$schema` 字段（指向 2.1.0 schema URI）。（来源：
  https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github 与
  https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning ，
  后者原文："Any valid SARIF 2.1.0 output file can be uploaded, however, code scanning will only use
  the following supported properties"）
- **ruff 原生支持 `--output-format sarif`**：官方 `--help` 列出的可能值为
  `concise, full, json, json-lines, junit, grouped, github, gitlab, pylint, rdjson, azure, sarif`。
  （来源：https://docs.astral.sh/ruff/configuration/ ，逐字核对）
- **semgrep 原生支持 `--sarif`**（及 `--sarif-output=VAL` 写文件）。（来源：
  https://semgrep.dev/docs/cli-reference ，"Output results in SARIF format."）
- **eslint 经微软官方 formatter 输出 SARIF**：`@microsoft/eslint-formatter-sarif`，GitHub 官方文档
  给出的 ESLint→Code Scanning 示例工作流即 `eslint ... --format @microsoft/eslint-formatter-sarif
  -o results.sarif` 后接 `upload-sarif` action。（来源：同上上传文档页的示例 workflow）
- 此外 CodeQL 原生产 SARIF（GitHub 文档："the code scanning results will automatically use the
  supported subset of SARIF 2.1.0"）；生态中还有大量转换器（clippy-sarif、cargo clippy→SARIF 等，
  见 https://github.com/psastras/sarif-rs ）。

结论：**"互操作/上传到平台"这一层，SARIF 2.1.0 就是事实标准**。

### 1.3 工具原生 JSON 格式（不走 SARIF 时）的字段与级数

- **eslint `--format json`：severity 是 2 级**。官方 formatter 文档的 JSON 示例中每个问题对象为
  `{ruleId, severity, message, line, column, ...}`，`severity: 1` 对应 warning、`2` 对应 error。
  （来源：https://eslint.org/docs/latest/use/formatters/ ，json formatter 示例，已逐字核对示例中
  `severity: 1` 与 `severity: 2` 两类）
- **ruff `--output-format json` 字段（本机 0.15.20 实测）**：
  `cell, code, end_location, filename, fix, location, message, name, noqa_row, severity, url`。
  要点：
  - **有 `severity` 字段，但 lint 诊断实测恒为 `"error"`**（ruff 不提供 warning/note 分级）；
  - **有独立 `fix` 对象**：`{applicability: "safe"|"unsafe"|..., edits: [{content, location,
    end_location}], message}`——修复提示是结构化独立字段；
  - 有 `url`（规则文档链接）、`code`（规则编号如 `F401`）。
  （来源：本机 `py -m ruff check --output-format json` 实际输出，ruff 0.15.20；官方文档
  亦列 `json` 为可选输出格式，见 §1.2 链接）

### 1.4 对设计问题的回答

- "2 级还是 3 级"：**行业没有强制定论，但唯一的跨工具标准（SARIF）是 3 级（+none）**；
  单工具原生格式倾向更少（eslint 2 级、ruff 1 级）。稳妥做法：内部模型按 3 级上限设计
  （note/warning/error 对齐 SARIF 词表），当前只用 2 级也不妨碍将来对齐。
- "修复提示独立字段与否"：**有定论——独立结构化字段**（SARIF `fixes[]`、ruff `fix` 对象），
  message 只承载人类可读描述。

## 2. 落盘开关与文件策略：显式开 + 覆盖是结果报告主流

### 2.1 Bazel JSON trace profile（对照项：运行数据类）

- **默认开启**："By default, for all build-like commands and query, Bazel writes a profile into the
  output base"；开关是 `--generate_json_trace_profile`，位置用 `--profile`。
  （来源：https://bazel.build/advanced/performance/json-trace-profile ，逐字核对）
- **文件名 = 每次调用一个**：`command-$INVOCATION_ID.profile.gz`，另有 `command.profile.gz`
  符号链接指向最新一次；**默认保留最近 5 份**（`--profiles_to_retain`），显式指定 `--profile`
  路径则关闭自动清理。（同上原文）
- 即：运行数据类落盘 = 默认开 + **调用 ID 命名累积 + 保留最近 N 份的垃圾回收**。

### 2.2 pytest `--junitxml`（结果报告类）

- **显式参数才写**："To create result files which can be read by Jenkins or other Continuous
  integration servers, use this invocation: `pytest --junit-xml=path`"——不带参数不产生文件；
  文件写到指定路径，每次运行覆盖该路径（写模式打开）。（来源：
  https://docs.pytest.org/en/stable/how-to/output.html ，"Creating JUnitXML format files" 一节）
- 同页也显示 JUnit XML 的演进是松散追加式的：`record_property`/`record_xml_attribute` 的官方警告为
  "using this feature will break schema verifications for the latest JUnitXML schema"（见 §4.3）。

### 2.3 coverage.py `.coverage` 数据文件

- **默认覆盖**："By default, each run of your program starts with an empty data set."；累积需
  **显式** `-a/--append`（"Append data to the data file. Otherwise it starts clean each time."）。
- 多进程场景用 `-p/--parallel-mode` **给数据文件名加唯一后缀**（各进程独立文件），再用
  `coverage combine` 合并；文件名可用 `--data-file`/`COVERAGE_FILE` 指定，默认 `.coverage`。
  （来源：https://coverage.readthedocs.io/en/latest/commands/cmd_run.html ，Data file 一节，逐字核对）

### 2.4 eslint `-o/--output-file`

- **默认只走 stdout**，落盘是显式参数：`-o, --output-file path::String  Specify file to write
  report to`；写到指定文件即覆盖该文件。（来源：
  https://eslint.org/docs/latest/use/command-line-interface ，`-o, --output-file` 一节；
  ruff 同款语义："`-o, --output-file` Specify file to write the linter output to (default: stdout)"，
  来源见 §1.2）

### 2.5 归纳

| 场景 | 工具 | 默认 | 文件策略 |
| --- | --- | --- | --- |
| 结果报告 | pytest --junitxml / eslint -o / pip --report / pytest-json-report | **不落盘**（走 stdout 或不产生文件） | 显式参数 → 固定路径**覆盖** |
| 运行数据 | Bazel profile | 默认开 | 调用 ID/时间戳**累积** + 保留最近 5 份 |
| 运行数据 | coverage .coverage | 默认开（采集即写） | 默认**覆盖**，显式 --append 累积，--parallel-mode 后缀分文件 |

结论：**结果报告类：显式开 + 单文件覆盖是行业主流**；需要历史时（我们的数据飞轮场景）唯一先例
是 Bazel 式"**时间戳文件名 + 保留最近 N 份**"，而非无限累积或固定文件覆盖。

## 3. stdout 向后兼容惯例：默认人可读 + 显式标志切机器格式（6 例实证）

| 工具 | 默认输出 | 切换机器格式的开关形态 | 来源 |
| --- | --- | --- | --- |
| eslint | `stylish`（人可读） | `-f/--format <name>`，`--format json`；官方描述 "default: stylish" | https://eslint.org/docs/latest/use/command-line-interface |
| ruff | `full`（人可读） | `--output-format json\|json-lines\|sarif\|...`；"The default serialization format is \"full\"" | https://docs.astral.sh/ruff/configuration/ |
| pytest-json-report（插件） | pytest 常规终端报告 | **opt-in 主开关** `--json-report`（默认保存为 `.report.json`，`--json-report-file=PATH` 改路径、`none` 不保存） | 官方仓库 README：https://github.com/numirias/pytest-json-report |
| pip | 人可读安装日志 | `pip install --report <file>`（显式文件路径，`--report -` 写 stdout）；22.2 引入 | https://pip.pypa.io/en/stable/reference/installation-report/ |
| terraform | 人可读计划摘要 | `plan -json`（"Enables the machine readable JSON UI output"）；`show -json <file>` | https://developer.hashicorp.com/terraform/cli/commands/plan 与 /terraform/internals/json-format |
| semgrep | 人可读文本 | `--json` / `--sarif` 独立布尔开关；`-o/--output` 显式落盘（"Default is to print to stdout"） | https://semgrep.dev/docs/cli-reference |

结论：6 个独立工具（不同语言生态）**全部**采用"默认人可读 + 显式标志切换"，未发现反例。
`validate --json` 沿用此惯例零风险。

## 4. 输出 schema 稳定性承诺先例：版本字段 + 只增不改有直接先例

### 4.1 Terraform `terraform show -json` 的 format_version（最完整的轻量承诺范本）

- 输出含 `format_version` 键（Terraform 1.1.0 起值为 `"1.0"`），官方承诺原文：
  - "We will increment the **minor** version, e.g. \"1.1\", for backward-compatible changes or
    additions. **Ignore any object properties with unrecognized names** to remain
    forward-compatible with future minor versions."
  - "We will increment the **major** version, e.g. \"2.0\", for changes that are not
    backward-compatible. Reject any input which reports an unsupported major version."
  （来源：https://developer.hashicorp.com/terraform/internals/json-format ，逐字核对）
- 这正是"版本字段 + 只增不改 + 消费方忽略未知字段"三件套的完整先例。

### 4.2 pip `--report`（Installation Report）

- 顶层 `version` 字段，承诺原文："It will change only if and when backward incompatible changes
  are introduced, such as removing mandatory fields or changing the semantics or data type of
  existing fields. … Tools must check this field to ensure they support the corresponding version."
- 22.2 引入，**23.0 时 bump 到 `1` 并宣布格式稳定**（"Changed in version 23.0: version has been
  bumped to 1 and the format declared stable"）；并明确其演进由 pip 自身流程管理而非外部标准。
  （来源：https://pip.pypa.io/en/stable/reference/installation-report/ ，逐字核对）
- 这是"先发布 → 观察一个周期 → 宣布稳定并定版本号"的演进路径先例。

### 4.3 SARIF 的 version/$schema 与 JUnit XML 的反面教材

- SARIF 文件顶层强制 `version`（GitHub 只接受 `"2.1.0"`）与 `$schema`（指向 2.1.0 schema URI），
  用"锁死大版本 + 外部 schema 校验"做稳定性（来源见 §1.2 两篇 GitHub 文档）。
- JUnit XML **没有官方规范**："There is no official specification for the JUnit XML file format and
  various tools generate and support different flavors of this format."（来源：社区事实标准参考
  项目 https://github.com/testmoapp/junitxml ）；pytest 对自定义属性/元素的官方警告
  （"will break schema verifications for the latest JUnitXML schema"）也印证其演进是无承诺的松散
  追加。（来源：§2.2 同一页）
- 对照结论：**不做承诺的格式（JUnit）走向 flavor 分裂；做轻量承诺的格式（Terraform/pip/SARIF）
  才能被下游放心消费**。

### 4.4 OTLP "接收端 MUST 忽略未知字段"（复核确认）

- OTLP 规范原文复核通过："OTLP/JSON receivers **MUST ignore message fields with unknown names**
  and MUST unmarshal the message as if the unknown field was not present in the payload. … ensures
  that adding new fields to OTLP messages does not break existing receivers."
  （来源：https://opentelemetry.io/docs/specs/otlp/ ，JSON Protobuf Encoding 一节，本次逐字复核）
- 与 W02 既有结论一致：自定义扩展字段对 OTLP 兼容消费方天然安全。

### 4.5 归纳

轻量稳定性承诺（版本字段 + 只增不改 + 忽略未知字段）**有充分先例支撑**，推荐直接照抄
Terraform 措辞：顶层 `format_version`（semver），minor 只增字段、major 才允许破坏性变更，
文档里写明"消费方应忽略不认识的字段"。
